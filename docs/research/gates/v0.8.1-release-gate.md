What this trades, stated plainly:

- **The helper is not exercised live.** No push or fetch goes through the draft
  `git-remote-proton.exe` in this gate. Basis: its source (`cmd`, `internal`, `go.mod`, `go.sum`)
  is unchanged since **v0.7.0**, whose release bytes passed a live gate through the installed
  helper: bootstrap push, update push, clone and strict-fetch check (`v0.7.0-release-gate.md`,
  step 6; staged exe `00f70579…`, the helper this machine ran until this sitting);
  `git diff v0.7.0 v0.8.1` and `git diff v0.8.0 v0.8.1`
  over those paths are both empty, and the Release workflow builds with the same recipe and the
  toolchain pinned by `go.mod`. Equivalence of the bytes beyond the version string is therefore
  inferred from identical source and recipe, not compared byte for byte.
- **The module change is covered where it lives.** #10 changes local git, registry and mirror
  handling, not anything on Proton. It is covered by 24 new tests in a suite of 187 (CI green under
  Pester 6.2.0, local 5.7.1), by the same behaviour exercised against the installed 0.8.1 below,
  and by the fleet verify, which runs the new classification over every registered repository.
- **The fleet verify is the tool's normal daily operation**, not a test write: it reports, cuts
  bundles for stale repositories and prunes by retention, and never rewires a remote or deletes a
  mirror (only Install, Repair and Uninstall do). Acceptance: exit 0, complete, no repository in
  `attention`, matching the pre-run baseline below.

Not taken: the formal live gate, whose marginal value here is procedure and a live helper push
over code identical to v0.7.0's gated bytes. The same stand-in was used for 0.8.0 (on the session
record; no 0.8.0 gate record exists in the repository). `docs/releasing.md` has no written rule for
when a stand-in is allowed; whether to add one is open with Craig.
