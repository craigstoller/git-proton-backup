# Proton CLI 0.9.0 certification — Implementation Plan

> **For agentic workers:** Standalone certification task, the same shape as the 0.8.0
> certification of 2026-08-13 — outside a full SDD stage, but not small: a binary audit with
> state snapshots, a 17-row live table, a smoke suite, a machine swap with rollback, a formal
> release-artefact gate and a consumer-pin adoption. Solo TDD or one implementer subagent via
> superpowers:executing-plans / superpowers:subagent-driven-development, peer-reviewed plan
> (this file), live certification at the end is Craig-directed. Steps use `- [ ]` checkboxes for
> tracking. Read `docs/research/gates/cli-0.8.0-certification.md` first: it is the runner log of
> the last time this exact procedure ran, and this plan assumes its lessons.

**Goal:** Certify `cli-drive@0.9.0` as the helper's exact allowlist version, confirm that no exec
site needs to change (the hypothesis below), close the design-doc pin drift the 0.8.0
certification left behind, write the upstream drift check into the release procedure with an
owner and a cadence, and ship as the next release — so that a fresh install, which Proton's
download page now points at 0.9.0, stops meeting an allowlist refusal as its first impression.

**Architecture:** one compiled-in token moves (`transport.CertifiedCLI`), guarded by RED/GUARD
tests against the real `--version` shapes; the 17-row live contract table plus a push/fetch smoke
re-pin every CLI behaviour the helper depends on against the staged 0.9.0 binary, and two
cross-version clones check that each build reads the other's writes; the machine swaps only after
all of that passes; the release artefacts are gated separately, per `docs/releasing.md`.

**Tech stack:** Go 1.27 toolchain (`go 1.22` floor in `go.mod`), the `internal/testcli` scripted
shim, the live contract table in `internal/transport/contract_test.go`, PowerShell 7 for the
staging/hash/snapshot steps, the Proton Drive CLI itself.

**Spec:** `docs/v2-remote-helper-design.md` § *CLI version allowlist* (the rule this plan
enforces), `docs/releasing.md` (the release and gate procedure), and the 0.8.0 plan
`docs/superpowers/plans/2026-08-13-cli-0.8.0-certification.md` as the procedural precedent. This
plan argues from those three; executors read them.

**Why now (facts established 2026-10-10):** Proton published `cli/v0.9.0` on **2026-10-05**
(`version.json` `ReleaseDate`; upstream `cli/CHANGELOG.md`). The download page and the
machine-readable feed advertise **only** 0.9.0, so every new install gets a build the shipped
helper (v0.8.1, certified `cli-drive@0.8.0+06e8c605`) refuses. The installed fleet is unaffected:
the machine still runs 0.8.0 (binary dated 2026-08-13; the CLI does not self-update), and the
daily backup plus fleet verify were green on 2026-10-09, after 0.9.0 shipped. The move went
unnoticed for five days because nothing checks the feed between releases — the 0.8.0 plan asked
for a weekly manual check and it was never written down; this plan writes it down (Task 1 step
5). One difference from August, observed on 2026-10-10 and **not** to be relied on: the direct
0.8.0 windows/x64 URL still answered HTTP 200 with the installed binary's exact byte size. In
August the 0.7.0 download vanished the day 0.8.0 shipped. Treat the 0.8.0 link as liable to
vanish; the archived copy is the rollback source either way.

**Scope of "first impression", stated:** what a new user meets is the allowlist's verdict on the
CLI the download page gave them. This plan exercises that verdict with the draft helper against
the certified CLI (Task 3 step 5's pushes). Two install paths exist and only one runs here: Task 3
step 4 runs the **upgrade-path** install on this machine (`install.ps1` from the tag's export,
module payload present — the 0.8.1 adoption's shape); the **fresh-install layout** a new user
receives (exe + sidecar + `install.ps1`, no module folder) is **not** re-run here, because it is
pinned hermetically by `tests/InstallHelper.Tests.ps1`, it was the Stage 4 gate's own install
step, and this release does not change `install.ps1` (Task 3 step 3 verifies the asset equals
the tagged blob, which equals v0.8.1's). Deliberately out of scope, with that reason.

## Global constraints (binding, inherited from the house rules)

- Hermetic tests only outside Task 2 (never `GPB_LIVE_ACCOUNT`); every `go test` with
  `-count=1`; `go test -timeout 40m` on the live table (the Stage 6 run-1 lesson: go's own
  10-minute default killed the 17-row table ~14 s short).
- PowerShell: prepend the machine PATH on every `go`/`git` call
  (`$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + $env:Path`);
  `Set-Location` does not persist between tool calls; `gofmt -l` false-positives on CRLF working
  copies — never "fix" line endings.
- **Scheduler, and what "quiet" means.** `ProjectsBackupDaily` fires daily at 12:30 PM and
  reaches `Invoke-ProtonBackupVerify` transitively; agent-side `schtasks /change` is denied
  (harness permission classifier + the system-settings rule, disclosed in the 0.8.0 plan's
  execution amendment). So the quiesce is **Craig's action at every kickoff** (Task 1, Task 2,
  Task 3), and re-enabling is **Craig's step on every exit path**, named in each task's final
  checklist. **Quiet is three facts, verified read-only at every kickoff and before every swap or
  install:** (i) `schtasks /query /tn ProjectsBackupDaily /v /fo list` shows `Scheduled Task
  State: Disabled` AND `Status` is not `Running` (a disabled task's instance already in flight
  keeps running — disabling stops the next trigger, not the current run); (ii) no backup worker
  process exists — `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match
  'backup-projects|ProjectsBackup|GitProtonBackup' }` is empty (the pwsh host that would spawn
  the CLI later, not only the CLI); (iii) no `proton-drive` process exists. If (i) or (ii) shows a
  run in flight, wait for it to finish (`Last Run Time` advances, `Last Result` set, the process
  gone) and re-check all three before proceeding. The only fallback, for Task 1 alone, is a
  VERIFIED schedule-window quiesce with a bound: the day's run has fired AND finished (the three
  facts), the next falls outside the window, Craig abstains from manual runs, and **if Task 1
  cannot finish before the next 12:30 it pauses, lets the run happen, re-snapshots state, and
  records the run in the evidence file before continuing** — so a scheduled run is never read as
  a 0.9.0-caused state change.
- **Credential Manager.** The CLI's auth session is
  `LegacyGeneric:target=ch.proton.drive/drive-sdk-cli/auth-session`. Its secret is NEVER read or
  exported. Metadata-only watch (`cmdkey /list` filtered: presence, target, type, user) before and
  after every staged-binary phase; any change = STOP. Rollback of the credential is MANUAL RE-AUTH,
  always reported, never silently absorbed.
- **State store and the restore rule.** `%LOCALAPPDATA%\proton-drive-cli` is snapshotted
  (copy + SHA-256 manifest) before the staged binary ever runs (Task 1 step 0.2), and again at
  Task 2 entry (Task 2 step 2). Snapshots live OUTSIDE the repository —
  `C:\gpb-cert\cli090\state-snapshot-<task>\` — because `.superpowers/` is not git-ignored and
  the snapshot holds the CLI's caches and logs; only the hash manifests and the evidence markdown
  go under `.superpowers\cli-090-cert\` (untracked; never `git add -A`). **Deltas are
  classified, not all routed to STOP:** an *init-class* delta (existing files changing: the two
  cache SQLite files and their `-shm`/`-wal`, `events.json`, the log appended) is recorded and
  the work continues; a *migration-class* delta (a new file or directory anywhere under the store
  or a new proton-ish directory under `%LOCALAPPDATA%` / `%APPDATA%` / `%USERPROFILE%`, a changed
  `clientUid.json`, a missing file, a credential change, or state the installed 0.8.0 can no
  longer use) is a STOP. **Every STOP that follows a staged execution — in Task 1 or Task 2,
  before or after the swap — ends with the same recovery before the scheduler resumes:** restore
  the latest snapshot (hash-verified after restore), confirm the installed 0.8.0 still works
  (`proton-drive --version` prints the 0.8.0 token; `filesystem list /my-files` exits 0 with the
  baseline rows), re-check the credential watch, report; if the auth probe fails, manual re-auth
  is the documented fallback. A restored snapshot's caches are older than the account (anything
  written after the snapshot — a fleet verify's bundles, this run's own fixtures — is unknown to
  them); that is ordinary CLI operation, the CLI re-syncs from the server through its events
  cursor on its next run, and the post-restore `filesystem list` is what shows it. The fleet is
  never left on an unverified CLI or a migrated state store.
- The helper never modifies or deletes foreign data; all live writes confined to
  `/my-files/GitRemotes/<this cert's roots>` (named per task below) plus the fleet verify's own
  writes under `GitBackups` (the bundles it cuts and the old bundles its retention prunes, exactly
  as the daily run makes them — `docs/releasing.md`'s stand-in wording); the four untouchables
  (`GitBackups` beyond that, `Sensitive Project Sources`, `Project Repo Bundles`, `ChatGPT Export
  Text Backup`) and `_cas-probe` are never touched **by this run** — the contract table's
  compiled-in default root `/my-files/_cas-probe/contract` is named in the brief because rule 8
  requires naming it, and it is never reached because `GPB_CONTRACT_LIVE_ROOT` is set in the same
  shell as `go test` and the table validates it fail-closed before any live call; **the evidence
  is positive, not an absence in the log** (a green table run prints no root path at all): Task 2
  step 3 prints the override from that same shell into the run log before `go test`, and lists
  `/my-files/_cas-probe` read-only before and after the table so an unexpected `contract` child
  or a changed row would show; verify-before-trash with full subtree enumeration; row-set
  comparisons on all six fields of rule 1 (`uid`, `name`, `type`, `creationTime`,
  `modificationTime`, `parentUid`), never raw JSON equality
  (`docs/research/gates/brief-checklist.md`, all nine rules), **with the run's own authorised
  activity named as the only expected timestamp deltas** (Task 2 step 6).
- Never push, tag, publish, or enable auto-merge; Craig directs each. No attribution trailers on
  commits (the 0.8.0 plan's `Co-Authored-By` rule is retired by the current house rule). Source-
  sourced claims about 0.9.0 are HYPOTHESES (H1–H5) until step 0 and the live table pin them;
  where reality differs, the code adapts under a re-frozen candidate and this plan gets a

- Plan-supplied code and plan-supplied counts are hypotheses too (`v2-sdd-runbook`: nearly every

  #   the frozen release CANDIDATE before tagging/publishing a pin-moving release,
  #   the INSTALLED helper (on PATH) between releases and after this release is installed.
  # -Cli defaults to the proton-drive the helper would spawn: the first one on PATH.
  param([string]$Helper = 'git-remote-proton', [string]$Cli = '')

  if ($w.Count -lt 1) { Stop-Drift 'feed malformed or no windows/x64 entry (fail closed)' }
