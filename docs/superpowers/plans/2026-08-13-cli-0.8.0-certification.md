# Proton CLI 0.8.0 certification — Implementation Plan

> **For agentic workers:** Small standalone task (chip-scale, like the 2026-08-12 verify work):
> solo TDD or one implementer subagent, peer-reviewed plan (this file), live certification at the
> end is Craig-directed. Not a full SDD stage.

**Goal:** Certify `cli-drive@0.8.0` as the helper's exact allowlist version, adapt the one
affected exec site, land the parked `-1` size sentinel fix at its natural moment (as an
independently revertible commit with an explicit cut line), and ship as the next release —
before the ~08-20 Reddit introduction post sends new users to a CLI our current releases refuse.

**Why now (facts established 2026-08-13):** Proton hosts ONLY the current CLI version — when
0.8.0 shipped, the 0.7.0 download disappeared, so every new user gets 0.8.0 and our allowlist
refuses it (`GPB_UNCERTIFIED_CLI=1` hint as first impression). Machine-readable latest-release
feed: `https://proton.me/download/drive/cli/version.json` (per-platform binaries + SHA-512;
macOS/Linux builds exist — feeds the port track later, out of scope here).

## Grounding: what is verified vs inferred

**Verified locally (hashes, code, live account history):** the staged binaries and their
digests; our exec sites' exact argv; the v1 module's CLI surface; `NewCLI`'s signature; every
0.7.0 behavior the Stage ≤6 contract table pinned.

**Sourced from the announcement (Proton SDK lead, r/ProtonDrive, 2026-08-13) — treated as
credible but UNVERIFIED until Task 1 step 0 audits the staged binary:** the conflict-strategy
split and its value vocabularies; "`-f` short flag survives"; the `version` up-to-date report;
"one breaking change" (the announcement's framing — completeness is exactly what step 0 and the
live table exist to test, and `filesystem download`/`list`/`info`/`create-folder`/`trash`
surfaces are unaudited until then).

- **The split, as announced:** general conflict-strategy option REMOVED; `-f,
  --file-conflict-strategy` (`create-new-revision` | `rename` | `replace` | `skip`) and `-d,
  --folder-conflict-strategy` (`merge` | `rename` | `replace` | `skip`).
- **Our exposure (code-verified on our side):** `internal/transport/cli.go` `upload()`
  (~:405-406) runs `filesystem upload -f <strategy> --json`; `UpdateRevision` passes `"merge"`
  (~:456) — folder-only in the announced 0.8.0 vocabulary; the file-side value whose HELP TEXT
  ("Create a new revision of the existing file") matches UpdateRevision's intent is
  `create-new-revision`. Whether its REMOTE semantics match (same node uid, no duplicate) is a
  hypothesis Task 2's invariants test. `CreateExclusive` passes `"skip"`, present in both
  vocabularies — its outcome/summary shape is likewise re-verified, not assumed. Our uploads
  are always single FILES (ref files, packs, marker) — `-d` should be irrelevant to us; step 0
  confirms the CLI does not now REQUIRE it.
- **v1 module unaffected at the COMMAND level (code-verified):** `GitProtonBackup.psm1`'s
  only CLI calls are `filesystem list`/`info` probes — no upload, no conflict-strategy flags,
  and no CLI-version allowlist (that gate is the v2 helper's). Residual risk is CLI-global
  behavior (auth/config/session-store migration, startup) — addressed STRUCTURALLY, not just
  reactively: Task 1.0 snapshots the config/session state before the staged binary ever
  executes, and Task 2.4's rollback restores state alongside the binary.
- **`NewCLI(exe string)`** (cli.go:44) accepts an explicit binary path; `NewCLI("")` resolves
  from PATH. Certification runs the STAGED binary by PATH-prepend for the one `go test`
  invocation; the machine install stays 0.7.0 until the swap step.
- **Staged binaries (SHA-verified 2026-08-13):** archived 0.7.0 at
  `C:\Users\craig\Tools\archive\proton-drive-cli\0.7.0\` (README.txt: provenance + SHA-256/512;
  Proton no longer hosts it); staged 0.8.0 at
  `C:\Users\craig\Tools\archive\proton-drive-cli\0.8.0-staged\proton-drive.exe` (SHA-512
  matches version.json's windows/x64 entry; 121,838,592 bytes).
- **Allowlist mechanics (Stage 4):** exact-token match against `--version` output; token
  constant + `uncertifiedCLIEnv` in `internal/transport/cli.go` (implementer confirms exact
  locations). The announced up-to-date reporting means version output is TEMPORALLY UNSTABLE:
  an update nag can appear only AFTER certification day (when 0.8.0 stops being latest), so
  the matcher must key on the token line alone — never on line count or position — and step 0
  must establish whether the check makes a network call (offline behavior of `--version` is on
  a path every helper run touches).
- **Parked Task 1 Important rides along (independently revertible):** `parseNodeJSON`
  (cli.go:115-131) leaves `Node.Size` at 0 on an `activeRevision` parse-miss, making the
  size-unknown arm unreachable in production. Fix: a `type:"file"` node whose revision size
  did not parse sets `Size = -1`. Blast radius is audited first (see Task 1.4), the commit
  stands alone, and the CUT LINE is explicit: if the audit or tests grow it beyond a
  contained change, it reverts to the Stage 7 backlog and this release ships without it.
  (Ledger: stage6 workspace `progress.md`, Task 1 parked entry.)

## Tasks

### Task 1 — Hermetic changes (TDD, `-count=1`, RED/GUARD labels)

0. **Staged-binary audit (hermetic — local exe, no account):** BEFORE the first execution of
   the staged binary, in this order: **QUIESCE for the whole certification window** — disable
   the scheduled verify task NOW, not at the swap (round-3 [Codex+Kimi+Gemini] convergent
   blocker: exposure starts here, and a background 0.7.0 verify mid-audit would both race the
   state diff into a false STOP and run against a possibly-migrated store; re-enable on EVERY
   exit path, success or abort). THEN locate the CLI's config/session state (0.7.0's —
   discover, don't assume; **explicitly check whether state lives beyond the filesystem** —
   Windows Credential Manager / registry / DPAPI — round-3 [Gemini]: if it does, a
   filesystem-only snapshot is not a rollback, STOP and adjudicate the snapshot strategy with
   Craig before proceeding) and SNAPSHOT it (copy + hash manifest) — the snapshot is the
   rollback's state half, taken at the true last-known-good moment because the scheduler is
   already quiet. Re-fetch version.json and confirm the
   staged SHA-512 is still the hosted windows/x64 build (early drift STOP — don't burn cert
   work on a stale binary). Then capture verbatim, into the task's evidence file: `--version`
   AND `version` outputs (both spellings; stdout vs stderr; exit codes; once normally, once
   with the network unavailable); `-h` for every command we invoke — `filesystem upload`,
   `download`, `list`, `info`, `create-folder`, `trash` — plus the top-level help. AFTER the
   audit runs: diff the config directory against the snapshot — the "no writes" assumption is
   verified, not asserted; any migration observed = STOP for Craig before anything else
   executes 0.8.0. **Offline acceptance criterion (round-2 [Codex+DeepSeek]):** `--version`
   offline must complete without hanging, within single-digit seconds, with the token line
   present; if it blocks on network, STOP — the decision (timeout wrapper, token caching, or
   accepting the latency) is Craig's, adjudicated before certification proceeds. From the
   captures: confirm the `-f` vocabulary; confirm whether `-d` is required for file uploads —
   **pre-defined fallback if required: `-d skip`** (our uploads never legitimately hit a
   folder conflict; skip is the never-touch-foreign-data value) — confirm `--json` survives
   on upload; confirm the error-signature matchers' CONTAINMENT semantics still hold against
   0.8.0's output shapes (they are substring matches, so appended nag lines should be inert —
   verify, and record as the accepted-risk note for post-0.8.1 nag injection); note any
   structured-error documentation (FUTURE migration candidate — this cert stays on pinned
   text signatures). Re-label Grounding inferences as facts where confirmed; where
   contradicted, STOP and re-plan (SUPERSEDED banner).
1. **Token capture:** from step 0's `--version` output, the exact `cli-drive@0.8.0+<build>`
   token becomes the allowlist constant; record the SDK line too.
2. **Allowlist bump:** certified token → the captured token. Matcher semantics (round-3
   [Codex] defective-fix correction — the round-2 "containment scan" wording would REGRESS
   the shipped matcher, whose implementation deliberately rejects containment because it
   admits `<token>-extra` suffixes; cli.go:~517): PRESERVE the existing whitespace-field
   equality / structural identity-line parse exactly as implemented — never loosen to
   substring containment. Hardening is about which LINES are considered, not how a token
   matches: tolerate extra output lines (the update nag) without becoming line-count- or
   position-sensitive. GUARD tests: (a) a synthetic "update available" line appended —
   certification still passes; (b) the certified token embedded INSIDE a nag sentence on a
   non-identity line — certification does NOT pass on that alone; (c) `<token>-extra` and
   prefixed variants — refused. GUARD: 0.7.0's token now REFUSES (exact-version philosophy —
   Craig-adjudicated since Stage 2; do not re-litigate). **Override de-trapped (round-2
   [Gemini]):** `GPB_UNCERTIFIED_CLI=1` mechanics stay, but when the detected token is the
   KNOWN-incompatible 0.7.0 token, the override warning additionally names the specific
   incompatibility ("this build's update path speaks 0.8.0's conflict-strategy vocabulary;
   pushes that update refs will fail against 0.7.0") — the escape hatch still opens, but it
   no longer fails opaquely mid-push (a selective hard-ban was considered and rejected:
   override means override; the cure for the trap is candor, not a second gate).
3. **Strategy value:** `UpdateRevision`'s `upload("merge", ...)` → `upload("create-new-revision", ...)`;
   both explanatory comments updated to 0.8.0 vocabulary (`create-new-revision` = new revision
   of the existing file; NOT `replace`, which TRASHES the remote node — the never-touch rule
   in the CLI's own terms). `internal/testcli` shim: implementer reads it first; if it
   validates `-f` values or models the skip transfer-summary, pin the new vocabulary and add a
   skip-summary fixture if none exists (the summary shape is load-bearing for
   `CreateExclusive`'s Refused detection and deserves hermetic coverage either way).
4. **`-1` sentinel fix (separate commit):** FIRST audit every `Node.Size` consumer
   (`grep -n "\.Size" internal/ cmd/` and read each site) INCLUDING serialization boundaries
   (round-2 [Gemini]: any `json.Marshal`/cache/log path that persists or emits a Node — a
   `-1` crossing a boundary that assumes unsigned sizes is in scope, not just conditional
   logic) and record the list in the evidence file — the fix proceeds only if all consumers
   handle negatives sanely (expected: the refs.go band gate and the heal-arm gate, both of
   which already branch on `size < 0`).
   RED tests: `activeRevision` absent; present but `claimedSize` missing; `claimedSize`
   wrong-typed; GUARD: genuine `"claimedSize": 0` still yields 0; note in the arm's comment
   that a genuinely negative `claimedSize` from the CLI is indistinguishable from the sentinel
   (accepted; the CLI has never reported negatives — C9). Confirm refs.go's size<0 arm fires
   for the parse-miss via the existing wrapper-transport test pattern (extend, don't
   duplicate); update the stale "the CLI never reports negative sizes" comment.

### Task 2 — Live certification (Craig-directed, gate discipline)

A short cert brief is written as part of this task, following
`docs/research/gates/brief-checklist.md` by reference (runner-asserted strings quoted from
code; confinement; `-count=1`; long timeouts INCLUDING `go test -timeout 40m` — the Stage 6
run-1 lesson). **Failure policy, split by mutation (round-2 [Codex] blocker — the blanket
retry-once rule could certify a failed mutating contract):** for READ-ONLY operations, a
clearly-classified transport failure (connection error text, verbatim-recorded) may be
retried once after ~60s. For MUTATING rows (uploads, trash, create), a failed or
lost-response attempt is NEVER blindly replayed: reconcile the remote state first (list the
fixture's parent, record what actually landed), then re-run on a FRESH fixture path; and the
update-path invariants include a revision-observability check — if `filesystem info --json`
exposes revision identity/count, assert exactly one new revision; if it does not, the
fresh-fixture rule is the guard and the gap is recorded as an accepted limit. **A single
OBSERVED post-reconciliation invariant violation on a clean attempt BLOCKS pending Craig's
adjudication — reproduction adds evidence, it does not decide whether the first violation
counts** (round-3 [Codex]: "only repeatable mismatches fail" must not waive an observed
duplicate node, changed sibling, or corrupted read-back; nondeterministic unsafety is still
unsafety). Retry classification is reserved for transport ambiguity alone. **Session
non-portability is its own STOP class (round-3 [Kimi]):** if the staged 0.8.0 cannot use the
existing session (wholesale auth errors across rows — not transport, not per-row contract),
that is neither retryable nor adaptable-by-code; STOP for Craig with the state evidence.

0. **Freeze the candidate:** record the helper commit SHA under test, both binary SHA-512s,
   AND version.json's windows/x64 SHA-512 as the drift reference, re-fetched now (round-2
   [DeepSeek+Kimi]: the drift gate compares HASHES, not version strings — Proton could re-cut
   0.8.0 with a different build; and it runs here, not only at release). Any code change
   after this point restarts Task 1's suite and the affected live steps — certification binds
   to an immutable revision, or it certifies nothing.
1. **PATH-prepend the staged 0.8.0 dir** for the contract invocation; verify
   `(Get-Command proton-drive).Source` IS the staged path in that shell; machine install
   untouched. **After the FIRST authenticated staged run, diff the config/session state
   against the Task 1.0 snapshot** (round-3 [Kimi]: the unauthenticated audit's diff cannot
   see a migration triggered by first authenticated use) — migration observed = STOP, same as
   step 0. The scheduler stays quiesced throughout (Task 1.0's rule).
2. **Contract table live** (`GPB_LIVE_ACCOUNT=1`, `GPB_CONTRACT_LIVE_ROOT` inside the brief's
   confinement): all 17 rows against 0.8.0, re-pinning node-JSON shapes, `notFoundSignature`
   / `alreadyExistsSignature` full text, C16, F1, and the upload outcomes. **Update-path
   invariants, stated falsifiably:** after `create-new-revision` over an existing ref file —
   same node uid as before (stable identity, no duplicate/renamed sibling), exactly one row
   for the name in the parent listing, read-back bytes equal the upload, sibling rows
   untouched. **Skip-path invariants:** `skip` over an occupied name leaves the remote node
   byte-identical AND surfaces as Refused through the transfer summary (the summary's shape is
   asserted, not just the exit code). A BLOCK here means 0.8.0 changed a contract — the code
   adapts under a new frozen candidate (loop to Task 2.0), never a patch-around — **with one
   carve-out (round-3 [Gemini]): a stable-identity failure (the node uid CHANGES under
   create-new-revision) is not adaptable; it breaks the helper's ref→node identity model and
   is a STOP for Craig as an architectural finding** (the CAS research memo expects identity
   to hold, which is exactly why a violation would be a design event, not a patch).
3. **Hierarchical + junk smoke (small):** one nested-branch push/fetch round-trip and one
   strict-fetch enumeration against a junk fixture under the staged CLI.
4. **Machine swap (only after 2–3 pass; reversible = binary + state):** the scheduler has
   been quiesced since Task 1.0 (round-3 correction — round 2 scoped the quiesce to the swap
   window, which left the earlier, larger exposure open); verify it is still disabled and no
   `proton-drive` process is running; hash-verify the archived 0.7.0 AND the staged 0.8.0
   again; copy staged over `C:\Users\craig\Tools\proton-drive.exe`; hash-verify the result;
   run `--version`; run one fleet verify; re-enable the scheduled task only now (or on the
   rollback path below — every exit re-enables it). **Surface map (round-2 [Kimi] — say which binary runs what):** the fleet verify is
   the v1 MODULE, which has no CLI allowlist and probes only `list`/`info` — it is the valid
   post-swap health check; the installed v2 HELPER (v0.6.0 bytes) certifies 0.7.0 only and
   will REFUSE the swapped CLI until this release's helper is installed — a known, accepted
   window on this machine (no production `proton::` remotes exist today), closed by the Task
   3 deploy order: publish → install the new helper → the window ends. **Rollback trigger,
   explicit:** if the version check or fleet verify fails, restore the archived 0.7.0 binary
   AND the Task 1.0 config/session snapshot (both hash-verified after restore), then run a
   post-restore auth smoke (`proton-drive filesystem list /my-files` exit code) — a restored
   snapshot can hold a server-side-invalidated session (round-3 [Kimi]); if the probe fails,
   manual re-auth is the documented fallback, reported to Craig, never silently absorbed —
   re-enable the scheduled task, and report. Before triggering, distinguish "0.8.0 broken"
   from "session needs re-auth" (the auth probe against the swapped CLI answers it) so a
   healthy swap is not spuriously rolled back. The fleet must never be left on an unverified
   CLI or a migrated state store the restored binary cannot read.
5. Cleanup + row-set comparisons per checklist.
